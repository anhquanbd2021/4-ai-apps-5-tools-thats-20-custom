Feature-by-feature guide

One bay, two ways to wire it

The bay mounts four AI apps on the left rail and five tools across the top. This page maps every control to the integration cost it exposes — and to the drift only a shared protocol removes.

Honest limits. Connectors here are deterministic fixtures, not live integrations. Real bespoke drift hides in auth flows, retry policies, and pagination — the payload shape is just the easiest one to see.

Start here

What this demo proves

Toggle bespoke → mcp: twenty patch cables unplug and re-route through the brass bus, and the counter ticks 20 → 9. Then grow the stack — a new tool costs four connectors in bespoke, one adapter in MCP. Finally probe Postgres: in bespoke the support chatbot's hand-rolled connector answers with a different shape than its three neighbors; in MCP all four answers are byte-identical.

The controls

What each one demonstrates

Control 01

Wiring mode

The bespoke↔mcp toggle. Bespoke fills every cell of the 4×5 matrix with its own cable; MCP replaces the grid with four client adapters and five server adapters on a shared bus.

Proves
M×N pairwise work collapses to M+N protocol adapters.
Key detail
Counter reads connectorCount() — the arithmetic is the model, not a hardcoded 20/9.
Control 02

Add a tool

Patches a new tool jack into the bay. Bespoke spawns one connector per app — each stamped B·T·S·M for the build, test, secure, and maintain work it inherits.

Proves
The failure mode: marginal cost grows with M in bespoke, stays at 1 in MCP.
Key detail
addTool() returns the added connectors — +4 vs +1, side by side.
Control 03

Add an app

Mounts a new app jack on the rail. Bespoke spawns one connector per tool; MCP spawns a single client adapter.

Proves
Symmetry: growth hurts on whichever axis it happens.
Key detail
addApp() mirrors addTool() — +5 vs +1 on the stock bay.
Control 04

Probe Postgres

Fires one fixed SELECT through every path to Postgres and prints each connector's payload card.

Proves
Duplicated connectors drift: support-chat answers {records:[…]} with NULLs dropped while the rest answer {rows:[…]}.
Key detail
driftReport() groups payloads — amber cards are the minority shape.
Control 05

Direction badges

Every cable carries a direction mark. Two bespoke Postgres connectors shipped SELECT-only and show →; everything else is ⇄ read-write.

Proves
MCP arrows point both ways — a connector can act, not just fetch.
Key detail
A write probe returns ok:false on the two read-only cables.
Control 06

Server-checked count

The counter badge is computed client-side, then cross-checked against GET /api/count?mode=…&apps=…&tools=… on the server.

Proves
Browser and server agree — the M×N vs M+N arithmetic is one rule, not a UI trick.
Key detail
Bad params get a 400 with an explanatory JSON body.

Run locally

Inspect the evidence

npm test         # unit + server contract + e2e failure scenario
npm run matrix   # CLI: the 4×5 grid, 20 vs 9, drift report
npm run check    # both
npm start        # serve the lab on :3000

Try node scripts/matrix.mjs --mcp --add-tool redis to watch a sixth tool land as one adapter instead of four connectors.

Limits

What this demo does not claim

  • Connectors are deterministic fixtures — real ones hide auth, retries, pagination, and rate limits.
  • Drift is seeded in one connector; real duplicated integrations diverge in subtler ways.
  • Read-only cables illustrate direction — a real MCP server still needs an authorization layer you build.
  • The count is structural, not a cost estimate — adapters still take real work, just once per side.
